# 长程稳定性对照

入口：`http://127.0.0.1:5173/#reliability`，后端 `backend/reliability.py`，前端 `src/ReliabilityPanel.tsx`。

财务对照三组：ReAct、Graph、Graph + 负 motif。客服尚无已支持的负 motif，因此只比较 ReAct 与 Graph。ReAct 是完整工具型 Agent，具有相同的批量工具调用、业务工具、执行预算和最终状态校验，不人为削弱基线。

## 实验协议

- 选择 1–30 轮，每轮每个策略执行一次完整任务；默认财务 3 轮共 9 次任务。
- 快照按 base、changed、exception 循环，同轮每组从独立的同一快照开始，记录 initialHash 验证配对。
- 每轮轮换策略执行顺序，避免某策略总是先执行；没有随机假数据或注入错误。
- 启动时冻结模型设置、工具契约、图和负 motif，保存完整经验副本及来源成本。运行期间不学习和替换经验，不将当前验证集反例用于其他组。
- 全部模型调用使用统一 model_client，关闭 thinking、开启单次响应批量工具调用。
- 保留错误、预算触顶、API 失败和取消结果。运行失败不会自动重跑；中断实验标记 interrupted，不补造缺失配对。
- 通过 API 启动稳定性实验时阻止其他常规/进化运行并发启动，以减少本服务内的延迟干扰。

## 图表和分母

累计曲线横轴是每组任务次数，纵轴是累计工具错误，包含修复前错误和负 motif 前置拒绝。相同曲线用不同线型及图例数值表示。

“有工具错误的任务”以该组所有已结束运行作分母，即使后来修复完成，仍计入发生错误的任务。“最终业务状态未通过 / 未完成”包含预算、取消和 API 失败。工具错误比例是错误尝试数/所有工具尝试数；图执行和模型决策调用单列，用于区分错误发生在哪一层。

前置拦截仍计入错误和尝试次数，另列 guardHits。非法 JSON 等调用也计入错误归属统计。全部读取另列，用于检查基线本来是否就没有读取错误。运行中的不均衡样本仅是进度，不是最终配对结果。

## 解释范围

“0/n 图执行错误”表示当前样本中已编译图步骤未出错，不表示整个 Agent 无错。确定性消除的是重复选择工具、绑定参数和执行依赖结构中的随机决策；工具契约变化、外部 API 失败、坏数据、图编译错误仍可能导致失败或回退。

当前重复使用开发合成快照，且每个快照记录较少；不能替代真实平台、未见任务和大规模运行的稳定性评测。工具状态校验也不评价报告文字：报告金额、数量和因果描述仍可能错误。页面明确显示报告文字未评分。

学习/影子验证成本保存在冻结经验的源成本字段中，在线汇总不混入来源成本；需评估长期摊销时另外计算。SDK 返回用量不完整时显示标记，不能按未知部分为零宣称收益。

API：GET/POST `/api/reliability`，POST `/api/reliability/{id}/cancel`，GET `/api/reliability/{id}/export`。实验结果保存在 `artifacts/reliability/{id}.json`，各次完整运行保存在普通运行目录。

## 首批真实运行

实验 `37f61cb2-c277-4e4c-bf38-e7d325a84db2`，qwen/qwen3.5-27b，3 轮、9 次任务。每组在 base、changed、exception 各运行一次。模型调用是真的，业务数据来自本项目合成 JSON，未访问 ERPNext/Zammad。

| 指标 | ReAct | Graph | Graph + 负 motif |
|---|---:|---:|---:|
| 运行数 | 3 | 3 | 3 |
| 有工具错误的任务 | 2 | 1 | 1 |
| 工具错误 / 尝试 | 2/64 | 1/51 | 1/63 |
| 结束且完整业务状态通过 | 2 | 2 | 3 |
| 模型服务导致未完成 | 1 | 1 | 0 |
| 图执行错误 / 调用 | 不适用 | 0/29 | 0/29 |
| 所有读取错误 / 调用 | 0/32 | 0/31 | 0/32 |
| LLM 请求（含失败请求） | 25 | 25 | 24 |
| 已记录 token | 129,504（不完整） | 131,919（不完整） | 142,388 |

两组图执行合计 58 次调用无工具错误、无图回退。ReAct 本次所有读取也没有工具错误，因此这些样本不能证明图降低了读取错误率。

第一轮 ReAct 的重复异常 entityId 错误、Graph 无工具错误，可以在逐次证据中并排展示。第二轮 Graph 再次出现同类 ID 错误。带负 motif 的版本没有重犯这类 ID 错误，但第一轮尝试将已不满足逾期条件的发票登记为逾期，产生另一类错误。其 guardHits 全部为 0，说明是模型直接生成合法 ID，未触发拦截；不能据单次组间差异证明提示的因果收益。

第三轮 ReAct 在第 8 次请求超时，Graph 在首次请求网络失败。它们仍计入整体未完成率，但不是确定性业务推理错误；Graph + 负 motif 先于这两组执行并完成，服务随时间变化构成混杂因素。不能将 3/3 对 2/3 描述为成功率提升，也不能比较不完整 token 得出成本收益。没有重跑或丢弃这两次失败。

本批是小规模连续运行验收，不是长期低错误率的统计证明。报告文字未做独立评分，0 工具错误不代表 0 事实错误。

## 数据从哪里来

当前任务数据在 `data/base.json`、`data/changed.json`、`data/exception.json`，由本项目构造；`backend/domain.py` 的 seed 读取 JSON，运行时复制到内存并应用工具状态变化，运行后保存 JSON/Markdown。它不是 SQL 数据库，也不是参考仓库提供的真实企业数据集。

部署的 ERPNext 使用 MariaDB，Zammad 使用 PostgreSQL，属于真实业务软件与数据库；其中 RSI 演示记录分别由本项目 `deploy/seed_erpnext.py` 和 `deploy/seed_zammad.rb` 初始化。官方项目提供表结构、业务对象、接口和校验，不是这批企业记录的来源。DSPy、GEPA、Hermes、Mem0 等参考项目也不是当前评测业务数据的来源。
