## 1. 核心要求与必须纠正的理解

1. 不新增人工岗位 SOP、业务政策层或预置角色工作流。业务约束来自当前用户请求、
   当前附件中用户实际提供的规则及澄清；没有明确的阈值、单位、口径就澄清，不能靠
   隐藏默认值缩短问题。开发者实现通用计数/关联/聚合工具不等于预定义业务流程。
2. 可复用 Graph 从正常执行轨迹诱导和修订：任务 -> 正常 Agent 执行 -> 实际调用、
   当前观察、错误/恢复及结果 -> RSI 提炼可执行结构与参数来源。LLM 可以生成 Plan、
   辅助解释轨迹和语义边界，但未执行的 Plan/DAG 不能直接发布为已验证历史经验。
3. 图匹配也从轨迹与反馈学习。不是先预定义问题类型，再把问题分类到固定流程。
   embedding/BM25 只能帮助召回，匹配须验证当前需求与图的执行兼容性。
4. 图编译时生成适用描述、语义槽、输入输出契约和拒绝约束；后续正常 train 的实际
   选择/绑定/执行反馈继续修订这些内容。不是只有图执行才有 RSI。
5. 复用覆盖读取、确定性计算、已有本地产物写入；真正跳过已确定工具的选择与填参，
   当前业务值重新读取/计算。不可确定的内容保留模型边界。
6. 三场景保持财务运营、客服运营、技术工单运营；工作台可自由输入并上传资料。
   普通演示工作区可关闭学习但只读使用已审核经验，训练实验必须有反馈维护。
7. 效率、效果、可靠性、进化和可展示性均需实际证据。约 30% 全量 token 节省是目标，
   不预设曲线形状、不制造错误/版本、不去掉冷启动/失败/恢复/匹配成本。

用户再次确认：**进化、效率、可展示性是本次重构的首要验收项**；效果和可靠性是
效率结论的质量门槛。每阶段交付必须逐项报告，不能只交代码或测试通过数量。

| 首要验收项 | 必须交付的证据 | 不足以验收的替代物 |
|---|---|---|
| 进化 | 正常在线任务反馈产生实际G结构修订、M匹配规则修订，各有来源、diff及后续任务使用/行为变化 | 仅G0创建、命中数增长、support累积、状态晋升 |
| 效率 | 同任务成对token、模型请求、串行latency与累计净节省率；标注G/M事件并包含全部学习/恢复开销，目标约30%全量token下降 | 只报热启动子集、模型调用减少、累计节省绝对值增长 |
| 可展示性 | 用户输入与拖拽上传→真实求解→可下载业务报告；同run轨迹/绑定、真实G/M差异、族内与累计收益曲线可点击回看 | 只有静态benchmark表、假进度、不可关联原运行的演化动画 |

自然任务中未观察到修订或未达到效率目标时，明确列为未达标并给出诊断；不通过
隐藏成本、改任务顺序或人为失败完成指标。进化前后的效率变化也须控制任务规模与
难度差异，不能仅凭曲线相邻就声称修订导致收益。

所附聊天记录里的“这才是当前机制”是设计讨论表达，不能覆盖现场代码核验：当前
实现仍有模型读取 Plan -> 本地 DAG 编译、固定 template 快速选择、workspace 图跳过
修订等路径。这些是重构对象，不能仅改 README 就声称轨迹诱导和匹配进化已实现。

## 3. 目标闭环：一个图经验包，两种反馈修订

```text
当前请求 + 当前附件 schema + 已审核图经验
                 |
       召回 -> 兼容性判断 -> 当前槽绑定
          /                       \
    完整/局部复用             没有可靠经验
          |                       |
    图执行 + 必要模型          正常 Plan + ReAct
          \                       /
             本次真实执行轨迹
                     |
     train：轨迹诱导/反馈修订与契约编译
                     |
     图经验包：执行图 + 可进化的匹配描述
                     |
               后续任务实际使用
```

“正常执行”可以有临时 Plan/DAG；不能因为当前模型生成了一个图，就把未执行节点加入
学习库。任务没有完整成功时，只保存诊断/失败约束；有有效恢复且最终通过时，才从
已执行且可验证的部分形成修订。不要复用过去的业务结果。

图结构版本 G 与匹配描述版本 M 分开记录。例如 G0 不变而 M0 -> M1 的适用范围变更，
可称为匹配机制改进，不得冒充 G1。仅支持度增加也不是规则修订；版本差异必须能解释。
无需新增独立 SOP 服务或庞大 IR；沿用 dict/JSON Schema/现有 runtime，把两种证据
放在同一经验对象或可追溯引用中，保持图和描述版本一致。

## 4. 轨迹诱导与完整图编译

- 收集实际 toolTrace/ledger：工具、参数、执行所有者、当前输出、成功/拒绝、时序与
  因果依赖。可记录显式简短 intent，不要求隐藏 thought。
- 从正常 train 的有效执行中识别读取/关联/聚合/筛选/证据/产物节点及数据依赖。
  将分页、重复逐记录调用折叠为循环；同批独立调用不能因轨迹相邻就编成依赖。
- 参数来源要可验证：当前表/字段槽、当前任务语义槽、上游输出/记录、受约束结构常量。
  支持嵌套数组/对象的绑定；只因为两次出现相同数值，不能断定数据依赖。
- 不能可靠泛化的参数和语义留模型边界；编译产物同时记录已覆盖与未覆盖的工作要求。
  如果模型辅助编译/描述提炼，计入 learning/compile 模型请求、token 和耗时。
- 真实历史轨迹的执行与当前任务公开约束共同限定适用范围。一个成功样本不支持任意
  类似业务；泛化门槛在实验前固定，不用 future/gold 为编译器补参数来源。
- 按当前工具契约执行确定性 compute。本地 artifact 依赖本次观察/计算/语义输出，
  实现运行内幂等和串行写入；回放、维护、匹配不得重新生成产物。
- 写节点仅限现有草稿、导出、报告；不新增付款、外部消息、改账或关单。
- 历史记录ID、tableId、evidenceId、metrics、selectedIds、摘要正文不可作为下次的
  字面答案。绑定仍须校验当前 scope/schema/types。

示例“读取 -> 订单聚合 -> 差额/分期/缺失 -> 报告”用于说明业务要求，不是允许
开发者按 finance-XXX 写固定图。工具可以通用，业务子图必须有实际轨迹和约束来源。

## 5. 在编译时形成、在反馈中修订匹配逻辑

不是训练集出现前写好 reconciliation/installments 等问题分类器，也不是给每族一个
固定路由关键词。通用的类型/schema/效果协议可以预定义，具体业务适用条件不能预定义。

### 编译输出的适用描述

每个图经验包至少记录：

- 根据来源请求、实际图与工具输出得到的任务目的、必需事实/交付要求。
- 图实际使用的表角色、键、字段/类型、关联基数、单位和计算/筛选操作要求。
- 实例可变槽及来源：如当前请求中的阈值、分期下界、期间、排序；必要的固定语义约束。
- 能完整覆盖的需求、只能局部覆盖的需求、必须保留模型处理的部分。
- 正常 train 的来源 run/图版本、有效参数来源、适用与拒绝证据。

描述可能需要模型辅助提炼，但必须由工具契约和实际轨迹检查。模型声称某图能完成
额外功能不等于图真的支持；不存在的节点/输出不能出现在覆盖证据里。

### 当前任务的选择过程

1. 使用本地召回，embedding 为可选优化，不作为唯一接受条件或本轮依赖。
2. 对照当前公开请求和 schema，验证已编译描述。复杂新语义允许一次有界结构化模型
   判断/提取当前槽，尽量合并正常 Plan；不为每个工具独立再请求模型填参。
3. 硬校验先于得分：字段、类型、单位、键、scope、操作与交付要求必须满足；召回
   高相似度不能覆盖硬校验。没有可靠当前槽时澄清或 Fallback。
4. 输出完整复用/局部复用/拒绝，并记录依据。只支持一类异常的图不能冒充已完成
   当前请求的三类；可以执行兼容子图，把缺少的工作交给正常模型流程。
5. 当前任务不得读取 family/template/workpackId/difficulty/expected answer 来选择图。
   这些信息仅留给实验统计；代码及模型输入都需验证这一点。

### 反馈修订

- 记录候选、选中图、适用描述版本、当前槽绑定、覆盖范围及实际执行结果。
- 正常 train 中绑定错误、需求覆盖不足、有效恢复等，提供正/负匹配证据。修订具体
  约束、槽、字段/单位要求或局部覆盖；不能只写一段“下次注意”的日志。
- 网络故障/用户取消/模型服务超时不自动作为语义不兼容证据。图已正确执行而报告
  措辞失败时，也不能无条件否定检索。区分检索、绑定、执行、报告/服务故障。
- 图支持当前条件变体时，把5分/8期绑定为当前值；不应为所有数值变化另建一张图。
  操作/字段/交付义务变化超出支持范围时，拒绝或生成有证据的扩展子图。
- 同一图的匹配修订必须在后续正常任务中真的改变选择/拒绝/局部覆盖，并展示来源。
  只改检索分数、日志或支持计数不证明选择质量提升。
- 学习不额外影子 rollout；test 无回写，产品只读加载不得修改共享版本；validation
  仅允许既有协议中的适用证据，不能从其反馈生成业务描述/Patch。

### 边界对照

| 新请求变化 | 应有行为 |
|---|---|
| 同语义换措辞、换记录 | 兼容时复用，不要求文本哈希相同 |
| 差额>5分改为>10分；分期>=8改为>=12 | 支持对应槽时绑定当前值，不照抄旧值 |
| >=8改为==8 | operator 也必须变化；不支持则拒绝该部分 |
| 取消与退款语义接近 | 只有当前字段、条件和工具能力确实支持时才可复用；语言相似不足 |
| 单一筛选改为多原因复核 | 原图只能局部覆盖时要说明并完成其余义务 |
| 金额分改为元或新增缺失关联 | 校验单位/基数/缺失处理，不能沿用错误条件 |

## 6. 用户财务样例：保留语义，不增 SOP

以下是用户最新给出的重构验收样例；不要假定它已在旧 V17 的冻结48任务中实际运行。
旧 frozen 财务 reconciliation 阈值为>1分，另族 installments 下界>=6，并非这个组合请求。

> 请根据这份订单、支付和商品明细做一份财务复核简报，范围只限本次附件。
>
> 按 order_id 汇总每个订单的支付金额、商品金额及运费。一个订单可以有多笔支付、
> 多条商品明细，不要把它们当作重复行直接删除。
> 请分别列出：支付总额与商品金额加运费总额相差严格大于5分的订单；最大分期数
> 达到8期的订单。两类可以重叠，不要合并后丢掉原因。
> 缺支付记录或缺商品明细的订单单独列为待核查，不能当成金额为零已完成对账。
> 给出附件内订单数、支付总额、商品加运费总额、各类复核订单数，附订单ID及证据；
> 金额展示为BRL并注明原始字段为分。
> 最后给出内部复核建议。即使某类没有入选订单，也请明确写0并说明筛选条件。
> 只分析和生成报告，不执行退款或改账。

该请求长度可接受，不为“自然语言看起来短”删掉决定结果的条件，也不将条件移到
隐藏 SOP/validator。模型可以自主决定查询和计算顺序；业务方说明结果口径是合理输入。

验收义务（只描述此样例，不写成所有财务任务的硬编码流程）：

| 项目 | 要求 |
|---|---|
| 范围/关联 | 本次附件的订单范围，按订单键聚合；支付与商品的一对多不能错误去重或直接联表放大金额 |
| 金额差异 | 两侧资料完整时，abs(支付-商品-运费)>5 cents；严格大于，等于5不入选 |
| 分期 | 有支付数据时计算最大分期，>=8；有无金额差异独立判断 |
| 缺失 | 缺支付/商品分别说明，金额对账标待核查；不把缺失一侧置0后宣称完成 |
| 多原因 | 保留差额、分期和不完整的独立集合、原因、计数与证据；允许重叠 |
| 总体指标 | 当前订单数、实际可见支付及商品/运费总额、分类数量；不能把缺失当确定业务真值 |
| 展示 | 原始分、显示BRL，转换不改变计算阈值；空集合明确0、条件及解释 |
| 成果 | 可读简报、分类订单清单、当前证据、内部建议；不执行外部业务写入 |

现有 publish_report 的 metrics+selectedIds 可以保存总体与并集，但单一 selectedIds
不能充分表达多原因和行级证据。按实际需要扩展通用 findings/groups 字段或等价结构，
使每组有原因、当前选中对象、数量和证据。它必须对两臂共享，渲染不能从私有答案补写。
不要为此新增一个偷偷完成整道题的 finance_review(taskId) 工具。

## 7. 重视问题构建：新版本资产和可核验难度

保留旧300任务、旧72工作包、用户 test/附件和所有历史工件。新建独立任务资产版本，
用户工作台仍不展示固定题库或把自由问题偷偷映射成 taskId。

**问题写法：多展示业务目标、约束与交付要求，少指定执行流程。** 用户问题应说明
范围、口径、阈值、缺失处理、重叠分类、证据、输出与禁止操作；不要给工具名、
调用顺序、图节点或“先调用A再调用B”的实现步骤。必要的业务定义必须保留，例如
“按order_id汇总、不得误删多笔支付”是正确性约束，不应为缩短文本而删除。
由Agent自行规划和执行，再由实际轨迹编译可复用图及匹配描述。验收任务材料时
检查是否把解题流程泄漏进题面；任务分组和私有答案也不能替代用户约束参与匹配。

建议新48条train组织为三场景×两个代表工作流组×八个不同实例，每组能观察多次复用、
修订后使用和两个四任务窗口；组标签仅供统计，不提供给 Agent/匹配器。
这是执行建议，不是旧V17 manifest的修改。为每组另留独立 validation/test，明确预算
内何时运行；资产数量不等于授权一次性跑完全部模型/Judge矩阵。

三场景业务方向：

| 场景 | 两个代表工作要求 | 需要真实展示的成果 |
|---|---|---|
| 财务 | 多原因订单财务复核；跨期金额/支付结构与关联完整性复核 | 金额总览、分类清单、明细/证据、口径与内部建议 |
| 客服 | 多源投诉升级与响应核查；期间变化及基于用户提供知识资料的内部跟进草稿 | 队列、不同原因、统计与文本证据、草稿及待核查项 |
| 技术工单 | 活动/标签/里程碑联合分诊；两份导出的变化与交接复核 | 原因与优先清单、变更对照、来源链接、内部交接 |

业务规则/阈值来自各任务，资料来自可追溯公开记录或用户提供文件。CFPB 不是完整企业
客服对话，GitHub Issues 不是内部服务工单；人工政策、前期导出或异常若确实需构建，
显式标注作者/注入来源，不能当真实生产数据；不为了触发 G1 注入工具故障。

实例变化需分离三种目的：

- 可复用变体：同工作目标的措辞、当前期间/数值槽、记录实例、已支持的字段名称绑定。
- 有效扩展/拒绝：增加真实交付要求、单位/关联基数变化、缺资料/含糊条件，观察局部
  复用、澄清、扩展或拒绝的行为；不把所有情况强求为 Fast。
- 规模变化：记录数、子记录数、文本体积独立控制，规模曲线单列。不要让在线轮次
  与所有难度特征完全绑定，然后把曲线变化都解释为进化。

难度特征至少记录主/子记录数、表数、关联基数、条件数/组合、交付组数、文本体积、
单位和缺失问题。不能仅给A/B/C。先审查三场景各一份完整材料，提供自然问题、附件、
公开约束、预期报告结构及私有评分范围；阈值/口径必须对 Agent 可见，私有部分只含真值。

财务主记录12-30、客服10-20、工单10-20可作为初始演示规模建议；按可用真实记录与
模型预算调整并冻结。不能只凭记录多就判断难，也不能通过重复复制原记录增加规模。

## 8. 反馈修图、实验与展示验收

执行步骤：

1. 只读审查旧轨迹和协议，明确编译输入/来源、图版本与描述版本、当前槽来源和计量。
   旧轨迹可诊断，不能预加载进声称“独立空库”的新实验；不覆盖旧 artifacts。
2. 先做一条财务完整链：用户样例 -> 冷启动真实执行 -> 轨迹编译 -> 当前绑定复用 ->
   多原因报告。把匹配描述与反馈同时接入，不先按题库固定模板做一个临时捷径。
3. 再推广到另外两场景及新资产，保持现有上传/历史/追问/下载路径和模型HTTP边界。
4. focused 协议测试验证无题库标签路由、描述来源、措辞/条件变体、类型与单位、
   嵌套依赖、缺失/空集合、多原因报告、本地产物幂等与只读加载。注入测试不是业务证据。
5. 新 runtime/manifest/评分/匹配反馈机制先冻结。小规模预检可取每场景同组3个正常
   train实例：两臂各9次，含修订后的后续任务机会。固定来源与预算，保留负向结果；
   没有系统性质量/维护/计量问题且预算条件满足后，再扩大新严格串行48-task对照。
6. 两臂同模型、工具、通用提示、资料、预算、共享恢复；Baseline可正常Plan但不学习，
   RSI独立空经验、仅学习此前train。run=model=read=1；任务对先后交替、各自顺序相同。
7. 正常成功轨迹支撑冗余裁剪、计算链编译、绑定/恢复修订或工作目标覆盖扩展，才建立
   结构变化子图。不要故意晚编译已验证节点来造G1；未知错误留下待修而非盲发图。
8. 给出至少一条图结构修订和后续使用链，以及一条匹配规则修订/实际后续行为链；
   两种改进分开验收，若没有自然发生则判该项未达标，不重复跑到好看。

阶段成本：召回、当前语义解析/选择、绑定、冷启动Plan、执行模型、轨迹编译/反思、
图维护/持久化、工具读取/计算/写入/恢复。实际provider尝试和未知usage另列；
局部毫秒计时可能嵌套，不能重复相加。新编译/匹配模型成本必须进入全量Agent预算。
Judge不是临时学习信号，成本单列，同模型不称独立验证；本次不自动新增裁判大矩阵。

展示三条不同曲线/账本：

- 同组按任务到达次数：单次相对Baseline的token/latency节省率，并标真实G/M修订事件。
- 累计节省率：1-sum(RSI)/sum(Baseline)，包含冷启动、拒绝、失败和恢复；同时保留
  单次波动，不用累计省下的绝对token越来越多冒充单位效率持续提高。
- 可靠性：任务最终成功/失败、错误/拒绝、恢复与上限次数。没有金标准的用户任务
  标人工审核，不能与实验硬通过混为一谈。

若检查可能平台期，预先固定同组相邻四任务窗口及条件，保持任务难度/规模分布可比；
八任务仅能做有限描述性检查，不证明理论瓶颈。不强求曲线单调或非线性。
视频以业务简报和清单为主，技术细节可展开查看轨迹来源、当前绑定、模型/图步骤与
G/M差异。全部点击关联同一run/输入/产物，不生成假实时进度。

## 9. 执行边界与交付

- 本文不发起付费模型运行，不解除已有预算暂停；执行 session 核验当前预算/在途任务，
  必要时先完成代码、协议测试和保存轨迹展示。不得因预算或网络问题静默恢复旧沙箱。
- 模型HTTP仅model_client.py，thinking=false；不覆盖.env、不泄露凭据、不自动换模型。
- train学习，validation/test冻结边界沿用。私有评分只能门控通过/拒绝，不给匹配/图编译/
  报告任何 expected metrics/selection；不以gold重写缺失业务真值。
- 只维护一个代码写入者，使用现有Python/FastAPI与React/TS；不新增不必要服务。
- 按模块边界作可审查提交，验证相关pytest、前端测试、构建、diff检查和三场景浏览器闭环。
- 最终交付：live URL、新任务材料及来源、可下载报告、图/匹配编译证据与真实修订/
  后续使用、新实验全量指标和失败账本、未达标项、录制脚本；更新项目状态文档。
