## 质量观察：执行成功不代表报告完全正确

财务报告正确识别了总应收、剩余应收、部分分配、多发票分配及重复银行引用，但存在以下实质性问题：

1. 将 Customer 的 `docstatus=0` 解释为“未提交草稿”。实际 Customer DocType 不支持 submit，这个值不能作为客户异常证据。
2. 将剩余应收与未分配款的 ¥9,300 差额归因于 ¥6,000 重复引用和 ¥3,200 未归属款，既缺乏业务依据，数值也不相等。
3. 对 payment_schedule 子表和表头差异直接归因于“展示未刷新”，没有从 API 获得原因证据。

客服报告正确识别 5 个未关闭工单、2 个首响超时、4 个未分派工单与高优先级事项，但也有需要评分器捕捉的语义问题：

1. 将 type=note 直接称为“内部备注”，实际种子文章 `internal=false`；文章类型和可见性是不同字段。
2. 已关闭测试工单 `close_in_min=1440`、解决时限为 480 分钟，`close_diff_in_min=-960`；报告却称其“在关闭 SLA 内关闭”，方向解释错误。
3. 对 owner_id=1 的系统未分派标识采用了“归属异常”的不确定表述，说明平台字典和元数据仍有必要补足。

这些问题保留在基线中，不通过修改报告掩盖。后续 graph-based RSI 应在相同工具和元数据条件下对比，独立评估业务结论、约束与成本；新增字段说明或确定性计算工具时，普通 ReAct 基线也应获得相同能力。

## 下一阶段的边界

业务平台部署到此已满足最小真实读取环境要求。下一阶段可实现“轨迹 → 带类型和参数依赖的任务图 → 前置条件检查 → 图复用执行 → 失败回退 → 校验后保存新版本”。不要把人工预写完整任务图直接当作自动自我改进结果。

先用内置沙箱验证图执行和写入约束，使用真实平台验证跨 API 的读取、参数绑定和报告证据。大规模评测前需增加任务变体、执行恢复演练、确定固定巡检时刻，隔离学习与测试任务；目前未声称 RSI 收益。
